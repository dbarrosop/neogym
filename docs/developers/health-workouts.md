# Apple Health workout import

`health_workouts` is a **private raw-import stream**, not a NeoGym `workouts` template or `workout_sessions` log. No app data is exported to HealthKit and the importer never writes to HealthKit.

Each row has a generated UUID `id`, `user_id` (cascade-deleted with the account), a stable HealthKit `healthkit_uuid`, and a `raw jsonb` object. `(user_id, healthkit_uuid)` is unique; user-role inserts force `user_id` from the session. Users can select/delete their own rows, insert `healthkit_uuid` and `raw`, and update only `raw`. There is no public access. Re-importing the same workout upserts `raw` without duplicating the row.

The iOS app requests **read access only to `HKObjectType.workoutType()`**. The raw snapshot includes HealthKit workout UUID, numeric workout activity type and its Swift description, start/end times (UTC ISO 8601), duration, active energy burned in kcal if available, distance in meters, stroke/flight counts, source revision, device, metadata, workout events and activity segments, plus workout/activity aggregate statistics as unit-bearing quantity descriptions. Nullable fields stay null. HealthKit does not provide a JSON serialization of an `HKWorkout`; this is an explicit best-effort projection of its workout-level properties, not an archive of the native object. Route points and individual heart-rate/energy samples are separate HealthKit objects that require additional permissions and are **not** included. Calories are calories **burned**, not food consumed; workouts do not contribute to nutrition's calories-in values.

Sync runs when the Workouts area opens and on the hub's pull-to-refresh while the signed-in app is active. A paginated anchored HealthKit query yields additions/updates and `HKDeletedObject` identifiers; the importer deletes matching backend rows before upserting replacements. An opaque HealthKit cursor is stored in on-device UserDefaults under a per-user key **only after** both backend writes succeed. Empty pages do not advance the cursor, since read permission can be denied without exposing that fact to the app; failures replay the same idempotent batch. No snapshot-wide deletion is inferred from an empty query. The first sync with no cursor imports all currently readable workouts. Deletions that occurred **before** a cursor was created or after local app data/cursors were erased cannot be recovered by the anchored feed; reinstalling the app without clearing backend rows may leave stale rows. Background delivery, web display, and automatic conversion to NeoGym sessions are out of scope.
