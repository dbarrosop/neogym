# Private progress photos — backend API

The backend exposes private photo history to signed-in users; no web, iPhone, Watch or agent photo screens are enabled by this phase. Deploying the write metadata would open the API even without UI. Keep production uploads and links closed until the hosted privacy and operations checks below are complete.

## Model and permission boundary

- `progress_photo_labels` is a plain admin-managed catalog with Front (`front`) and Back (`back`) seeded in order. A referenced label cannot be deleted. `user` may read the catalog; anonymous clients cannot.
- `progress_photos.id` is both the primary key and the foreign key to `storage.files.id`. Separate UUIDs may share a date and angle. Read `progressPhoto` by ID or page `progressPhotos` by `(takenOn DESC, createdAt DESC, id DESC)` with an optional label filter; continue strictly after the complete last tuple. `takenOn` is a calendar date (`YYYY-MM-DD`, years 0001–9999), not a time or a date inferred from the image. The official clients apply the local-today rule, not the database.
- `user` may insert its own photo through `insertProgressPhoto` (`id`, `takenOn`, `label`; `userId` is preset) and correct only `takenOn` and `label` through `updateProgressPhoto`. The database locks the file and checks that it is recent, not queued or retired, completed, in this bucket, uploaded by the owner, named `progress-photo.jpg`, detected as `image/jpeg`, 1 byte–5 MiB, and has no custom Storage JSON metadata. Neither identity can be reassigned. MIME detection does not validate a full decode or strip embedded EXIF; the official client must re-encode the image without source metadata.
- The dedicated `progress_photos` Storage bucket requests `Cache-Control: private, no-store` and disables presigning. REST reads (original, HEAD and transformed variants) and GraphQL file reads require the uploader's bearer and an existing matching Auth row. Public `exercise_images` access is unchanged. No app role can replace a progress file or delete a photo row directly. A credential delegated with the ordinary `user` role has the same access for its owner even without a purpose-built photo client.
- Storage REST uses the same file permissions as Hasura and Constellation. Consequently generic `insertFile` can initialize a pending row, but cannot set its owner, `isUploaded`, `etag` or custom metadata; it cannot make a linkable file. Generic `deleteFile` can remove the user's own progress file metadata and cascade to the photo, but does not synchronously remove the object. Use REST for bytes and deletion, not a public or presigned URL. No progress writes are granted for the exercise bucket.

## Upload and retry

1. On explicit submit generate one new **canonical lowercase, hyphenated UUID** and keep it in memory. Send one file to authenticated `POST /v1/files` as multipart `file[]` with filename `progress-photo.jpg`, `bucket-id=progress_photos`, and one `metadata[]` part with `{"id":"<uuid>"}` and no other metadata. Wait for that ID with `isUploaded: true` in `processedFiles`. Storage detects the MIME from bytes, not the request header.
2. Link that UUID with `insertProgressPhoto` within **45 minutes** of file-row creation according to the database clock. A lost upload response can be reconciled by reading the owner's `file`: link an uploaded row or poll a pending row within a bounded retry budget. Before any link attempt, a missing row permits a same-ID upload retry only if initialization never committed. A committed initialization reserves the UUID even if the upload later fails, is abandoned, or is deleted. A rejected retry or expired attempt may be restarted only by explicit user action with a new ID; do not silently re-upload or create another submission.
3. Once linking was attempted, read `progressPhoto` first. A matching linked row is success; otherwise retry only the link to the existing uploaded file. Never recreate a deleted file. Before linking, Cancel may attempt REST DELETE of a known completed, unlinked file. Do not delete a still-uploading file; after an uncertain link reconcile first, rather than claiming cancellation.
4. After delete confirmation, call authenticated `DELETE /v1/files/<id>`. Removing the file row cascades to the photo. Reconcile lost or failed responses by reading the photo and surface a retry if it is still visible. A missing row or 404 proves inaccessibility, not physical deletion. Deleting an Auth account cascades to photo rows and revokes even unexpired JWT access to the files; it leaves file rows and objects for cleanup.

## Cleanup and evidence

The scheduler sends authenticated POST requests to `/v1/progress-photos/sweep` every 15 minutes. Hasura supplies `NHOST_WEBHOOK_SECRET` as `nhost-webhook-secret`; the Node 24 Function uses its server-only admin credential, ignores all caller selection fields and emits only status and counts (`selected`, `deleted` for REST 204, `missing` for REST 404, and `failed`). The SQL claim takes at most 20 unlinked files older than **60 minutes** from this bucket, including incomplete and deleted-account rows; a 10-minute cooldown prevents closely spaced invocations from repeatedly claiming the same row. It locks each candidate against attachment and rechecks for a link before committing the claim. A claimed file can never subsequently be attached. The Function deletes via Storage REST, with timeouts and bounded parallelism. A later scheduled run can retry rows still present. Monitor claim/delete failures and the age of the oldest eligible file/queue entry from admin-only diagnostics; do not log IDs, payloads, URLs or credentials from the sweep.

The local Storage 0.17.0 / Hasura v2.49.2-ce / Constellation 0.8.1 / Auth 0.53.0 / Functions Node 24 stack was exercised with synthetic fixtures only. An initial run used OTP bearers. The repeatable suite signs temporary fixture accounts in through Auth without sending email, checks local privacy headers and warmed owner/foreign variants, and observes MinIO independently after normal owner REST delete and authenticated scheduler-driven sweep. They also check that an in-flight SQL attachment and an already-linked old photo survive selection, and cover the interval where a file is too old to link but not yet eligible to sweep. This demonstrates SQL eligibility and ordinary object deletion, not the maximum lifetime of an incomplete request or hosted CDN behavior.

Storage's independent `storage.files_to_delete` worker handles metadata-only and partial REST deletes. An earlier local probe observed enqueue and verified the synthetic object's continued presence after 90 seconds; that probe did not establish a drain time and its queue fixture was left untouched. Storage 0.17.0 source uses a 24-hour age threshold and a 24-hour worker interval. **Eventual ordinary queue drain is a provider assumption for v1, not a passed test or a physical removal SLA.** In addition, Storage 0.17.0 can use a noncanonical request UUID as the upload key while later operations use the normalized UUID, and a put may finish after incomplete-file deletion and queue acknowledgement. The operator accepted these two residual cleanup limitations for v1. The single-use reservation prevents reuse of the typed UUID even after acknowledgement; the 45/60-minute gap reduces contention but neither measure guarantees removal of bytes retained by those provider behaviors. The limitations do not change the owner-only access requirement. No provider fault was reproduced in this shared stack.

Before opening production writes, verify the deployed Storage and Node versions, real bearer access and denial through the CDN (including an owner-warmed transformed response), private cache headers and presign denial, recurring authenticated scheduler delivery and observable outcomes, normal deletion and account-deletion cleanup with independent object checks, and ordinary queue behavior. Report any retained live bytes separately from provider backup retention. Neither a queue entry nor a 404 nor absence from MinIO establishes how long backups retain a copy.

## Rollback

First revoke file inserts and photo links while keeping existing reads, deletes and the sweep available. Before either destructive down migration, obtain operator authorization; drain or explicitly purge only the dedicated bucket through Storage and verify object absence independently, including queued files without metadata and any provider-retained keys. Keep cleanup on until the backlog is resolved. Remove feature tracking before dropping tables/functions; the down scripts refuse to discard reservations while progress rows or associated queue entries remain, but cannot verify byte absence. Never reset an existing developer volume or invoke an account-wide orphan cleanup to validate this rollout.
